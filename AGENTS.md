# android-notification-bridge

Forwards Android notifications to a macOS menu bar app while the phone screen is off and the phone is plugged in.

Use case: the phone sits charging on a desk at work, screen off and in silent mode so it doesn't interrupt (eg. meetings). Without the bridge there's no way to see a notification's contents without picking up the phone; Android can't be made to wake the screen and show new notifications on the lock screen. The Mac notification is the only alert, so it's what decides whether the phone is worth picking up (eg. a message from family). Forwarding latency matters, and so does noise: a forwarded junk notification (backup progress, etc.) is an interruption, and retracting it afterwards doesn't help because it's already been seen.

- `android/` - Kotlin app, no third-party runtime dependencies (tests use junit and org.json). `NotificationListenerService` -> `Forwarder` (one background thread per paired Mac, so an offline Mac doesn't delay the others; a failed discovery skips that Mac for 60 s) -> TCP to each Mac.
- `mac/` - SwiftPM package. `BridgeCore` (crypto, protocol) + `NotificationBridge` (SwiftUI `MenuBarExtra`, `LSUIElement`). `make build` assembles `build/Notification Bridge.app` and signs it with the first Developer ID in the keychain (hardened runtime), falling back to ad-hoc; `make install` copies to `~/Applications`. Keep a single installed copy: duplicate bundles with the same ID confuse LaunchServices. Clicking the About window's icon plays a cracktro easter egg (`Cracktro.swift` renders 320x200 indexed frames, `Chiptune.swift` synthesises the music live via `AVAudioSourceNode`, `Font8x8.swift` is the bitmap font).
- `testdata/vectors.json` - shared crypto test vectors; both test suites read it, proving interop. Generated by `testdata/generate.py` (uv script, OpenSSL via `cryptography`), an independent third implementation of the protocol; inputs are fixed so it's reproducible.
- `icons/` - source of truth for icons. `make icons` at the repo root copies `icons/mac/AppIcon*.png` into `mac/Resources/Assets.xcassets/AppIcon.appiconset/` (compiled by `actool` during `make build` into `Assets.car` + `AppIcon.icns`), the menu bar PNGs into `mac/Resources/`, and `icons/android/res/` into `android/app/src/main/res/`. Never edit the copies. Menu bar icon is `MenuBarIcon.png` (18px) + `@2x` (36px), black on transparent, used as a template image. Icons are modified Material Symbols, so they're Apache-2.0 (`icons/LICENSE`); the rest of the repo is MIT (`LICENSE`).

## Protocol

- Discovery: Mac advertises Bonjour `_notifbridge._tcp` with TXT `pk` = base64 raw X25519 public key. Phone pins up to 3 Mac keys, each chosen explicitly via "Add Mac" in the app (never auto-pinned), and sends every message to all of them.
- Connection per message. Frames are u32 big-endian length + payload (max 64 KiB).
- Frame 1 (hello): `0x01 || phone static pub (32) || ephemeral pub (32) || device name utf8`.
- Following frames: AES-256-GCM `nonce (12) || ciphertext || tag (16)` of JSON `{type: posted|removed, key, package, appName, title, text, ts}`.
- Key: HKDF-SHA256(ikm = DH(phone static, mac static) || DH(ephemeral, mac static), salt "notifbridge/1", info = phone pub || eph pub || mac pub).
- Mac replies one status byte per message: 0 delivered, 1 pending approval (buffered until allowed), 2 denied, 3 rejected (bad/stale >5 min).
- Changing crypto or framing requires updating and running `testdata/generate.py`, then updating both `Crypto.swift` and `Crypto.kt`.

## Building

- `make test` / `make build` at the repo root run both test suites / build both apps (debug APK, locally signed Mac app).
- Mac: `cd mac && make test build`. `make test` works with just the Command Line Tools, but `build` needs `actool`, which only ships with Xcode, so `xcode-select` must point at Xcode; `check-env` / `check-build` / `check-notarise` targets fail fast on that and on notarising with no Developer ID. SwiftPM's own sandbox must be disabled (`--disable-sandbox`, already in the Makefile); inside Claude's sandbox swift build still fails, so run unsandboxed.
- Android: `cd android && make test build`. `make install` / `make run` push the debug APK over `adb` (and launch it) to the one connected physical device (emulators are ignored). `make run-emulator` does the same on an emulator, booting AVD `$(AVD)` (default `Samsung_S25`, API 35) first if none is running. Used for UI checks before testing on the real phone; it can discover and pair with a Mac on the LAN. `JAVA_HOME` defaults to `/opt/homebrew/opt/openjdk`. The SDK comes from `sdk.dir` in `android/local.properties`, else `ANDROID_HOME`; `check-env` / `check-release` / `check-device` targets fail fast on a broken JDK, missing SDK, keystore or passwords, or no adb device. Gradle needs local socket binding (unsandboxed). compileSdk 37.2, minSdk 34.
- Version lives in root `VERSION` (x.y.z); build number / versionCode is `x*10000 + y*100 + z`. Mac `make build` writes both into the bundle's Info.plist (not the source plist); gradle reads it for `versionName` / `versionCode`.
- Release APK (`cd android && make release`) is signed with `release-keystore.jks` at the repo root (untracked, alias `release`), passwords from `KEYSTORE_PASS` / `KEY_PASS` in `android/local.properties`. Debug builds use the debug key, so switching a phone between debug and release needs an uninstall.
- `cd mac && make notarise` builds with a secure timestamp (plain `build` uses `--timestamp=none` to stay offline), submits to Apple with `notarytool` using keychain profile `notarytool`, and staples the ticket.
- `make dist` at the repo root builds both apps (Mac notarised) into `build/notification-bridge-<version>.zip`; `make release` publishes it as GitHub release `v<version>` via `gh`, tagged at HEAD; it refuses (before building) if the tree is dirty, HEAD isn't pushed, the clone is behind `origin/main`, or a release for `VERSION` already exists.
- Gate uses `EXTRA_PLUGGED`, not `isCharging`: Samsung battery protection stops charging at 80-85%.
- Silent (`IMPORTANCE_LOW`) notifications are held for 5 s, then forwarded from their latest state if still active and not noise. Backup notifications (Samsung Cloud, WhatsApp) are first posted plain on a silent channel, then re-posted as ongoing or foreground-service between 4 ms and 0.8 s later, so the first post alone looks forwardable. Alerting channels are forwarded immediately.
